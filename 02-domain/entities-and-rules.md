# Entities, Value Objects, and Business Rules

> **Instructions:** This document outlines the building blocks of the domain following the DDD tactical model.
> It translates domain knowledge into clear application code specifications and aggregate invariants.

> **Stack note:** Simple Stock Flow is built using a C# .NET Core Domain Core layer, utilizing Entity Framework Core configurations as the persistence adapter to map fields into the centralized PostgreSQL 16 `sales` engine schema (§0 / §12).

---

## Tactical DDD concepts

### Entity
An **Entity** is an object defined by its thread of identity, not its raw attributes. Two entities with identical structural fields remain distinct if they hold unique primary identification keys (§2).
✓ Entity: Product (stays the same entity even if its stock counts or prices shift §2.2)
✓ Entity: Sale (an immutable record tracked via its unique transaction UUID §2.3)
✗ Not an entity: Money (15.50 COP == 15.50 COP regardless of instances)

### Value Object (VO)
A **Value Object** is an object defined strictly by its combined attributes; it possesses no identity key of its own. It is immutable — changing a field yields a distinct new instance (§2).
✓ Value Object: Money (representing unit amounts and scale boundaries §2.2)
✓ Value Object: Quantity (wrapping validation limits for item counts §2.4)

### Aggregate
An **Aggregate** is a tightly cohesive cluster of entities and value objects treated as a single transactional unit. It is governed by an **Aggregate Root** which acts as the exclusive gateway; external components can only read or mutate internal nodes by executing public methods on the root (§2).

**Golden rule of the Aggregate:** Transactions do not cross aggregate boundaries. If a routine changes multiple states, the execution must be atomic inside the modular unit of work loop (§2.3 / ADR-001).

## System entities

### Entity: Product

**Context:** `SalesManagement` Module (§2)

**Description:** Represents a concrete commercial item within the active catalog, controlling pricing thresholds and available unit stocks (§1).

**Attributes:**

| Attribute | Type | Description | Required | Rules |
|-----------|------|-------------|---------|-------|
| `id` | UUID | Primary identification key | Yes | Generated by the application core (§3) |
| `name` | varchar(200) | Item catalog name | Yes | Pruned and whitespace-trimmed on input (§2.2) |
| `price` | numeric(18,2) | Current unit price value | Yes | Handled by `Money` value object; must be > 0 (§1 / §2.2) |
| `stock` | integer | Active unit stock counts | Yes | Enforced to remain >= 0 via engine checks (§2.2 / §4) |
| `category_id` | UUID | Reference category link | Yes | Relational foreign key constraint (`FK-1` — §5) |
| `image_key` | varchar(512) | Opaque asset storage tag | No | Replaces raw byte storage; empty handles read as `NULL` (§1 / D-08) |
| `deleted_at` | timestamptz | Shadow flag for soft deletion | No | Managed as an EF shadow property for query filtering (§2.2 / ADR-003) |
| `xmin` | xid | Engine concurrency token | Yes | System shadow column driving optimistic concurrency (D-04 / T-10) |

**Lifecycle / States:**

[Active Catalog Product] ──(Product.Withdraw / Restock)──▶ [Updated Stock State]
│
(T-09 Soft Delete)
▼
[Logically Deleted Asset] (Filtered from runtime visibility via ADR-003)

**Invariants (Core Business Rules):**

* **INV-PROD-001: Non-Negative Stock Limits**
  * **Rule:** Product stock counts must remain greater than or equal to zero after any state change.
  * **Violation:** Engine rolls back if stock drops beneath zero, throwing an invariant breach exception (§2.2 / `ck_product_stock_non_negative`).
* **INV-PROD-002: Strictly Positive Catalog Pricing**
  * **Rule:** A product unit cost must be greater than zero (`price > 0`).
  * **Violation:** Domain constructors intercept and block zeros or negative numbers (§2.2 / §4 · T-20).

## System Value Objects

### Value Object: Money

**Description:** Encapsulates core financial price tags without currency column desynchronization, assuming a single-currency baseline system model (§1 / D-05).

**Attributes:**

| Attribute | Type | Description |
|-----------|------|-------------|
| `Amount` | decimal | Raw monetary decimal numbers mapped to `numeric(18,2)` (§3) |

**Validation rules:**
* Amounts can never hold negative numerical symbols.
* Implements static rounding logic configured strictly to 2 decimal places using `MidpointRounding.AwayFromZero` before database writing routines execute (§2.2).

## System Aggregates

### Aggregate: Sale

**Aggregate Root:** `Sale` Entity (§2.3)

**Internal entities:**
* `SaleItem` — Internal transaction row representing a purchase line; cannot exist or be updated outside its parent root context (§2.4).

**Value Objects:**
* `Money`, `Quantity` (§1)

**Aggregate invariants:**

* **AGGR-SALE-001: Historical Item State Freezing**
  * **Rule:** Adding an item to the sale requires pulling and duplicating the name, original category name, and current unit price from the product state to hardcode them safely into the immutable transaction line (§1 / §2.4 / D-06).
  * **Violation:** Fails if live catalog references bleed into old records, preventing report desynchronization (ADR-004).
* **AGGR-SALE-002: Distinct Product Constraint**
  * **Rule:** A single product identifier cannot be listed across multiple detail rows inside the same transaction scope (§2.3).
  * **Violation:** Blocked by application lookups and verified at the database index tree layer (§2.3 / `IX_sale_item_sale_id_product_id`).

**Why do these objects form an aggregate?**
> A sale record and its line item details represent an inseparable financial boundary. An item line holds no business meaning or identity lifecycle without its parent transaction header, and database cascades guarantee they share a unified storage lifespan (§2.4 / `FK_sale_item_sale_sale_id`).
